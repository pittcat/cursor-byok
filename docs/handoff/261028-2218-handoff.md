1. **确认故障链**
   - Cursor 用户设置 `~/Library/Application Support/Cursor/User/settings.json` 中 `"http.proxy": "http://127.0.0.1:58597"`，即 Cursor 全量 API 流量走 BYOK 桌面应用内置代理。

   - 端口（见 `~/.cursor-byok-v3/cursor-byok.db` 的 `service_settings` 表 `network_ports`）：代理 **58597**，内嵌服务 **58317**。
   - Cursor 服务端日志：`~/.cursor-byok-v3/logs/cursor-byok.2026-10-28.log`。

2. **定位到失败点（已确认）**
   - 报错文本：`protobuf decode error: failed to decode Protobuf message: ...`
   - 来源：`server/src/error.rs:34`（`Error::Protocol`）→ 由 `server/src/api/cursor/bidi.rs:178` 的 `agent::AgentClientMessage::decode(payload.as_slice())?` 抛出 → 调用点 `server/src/api/cursor/handlers.rs:235`（`bidi_handler`）。
   - **关键顺序问题**：`bidi_handler` 先解码整条 `AgentClientMessage`，再根据 model_id 决定「本地 BYOK / 转发官方」。解码失败时直接 400，因此原生模型请求也一起坏掉——这解释了用户「不用 BYOK 模型也用不了」的现象。

3. **真实错误样本（日志实证）**
   - `2026-10-28T13:43:13` 起多次：`AgentRunRequest.conversation_state: AgentClientMessage.message: invalid wire type value: 6`
   - `2026-10-28T14:06:51/54/59`、`14:07:08`：`ConversationStateStructure.summary: AgentRunRequest.conversation_state: AgentClientMessage.message: invalid wire type: EndGroup (expected LengthDelimited)`
   - `2026-10-28T14:10:03/05/10`：`ConversationStateStructure.summary: ... invalid wire type: SixtyFourBit (expected LengthDelimited)`
   - `~/.cursor-byok-v3/logs/cursor-byok.2026-10-26.log` 中还有 `ConversationStateStructure.summary / file_states / plan` 的同类错误。
   - prost 的 `DecodeContext` 采用**最内层在前**的格式，因此失败点始终在 `ConversationStateStructure` 的**顶层 tag** 处，而不是某个已知嵌套消息内部。
   - 报错位置随内容变化（summary/plan/file_states/顶层），说明是内容相关的解析错位，而非固定字段号不匹配。

4. **Schema 对比（已确认，本轮最重要结论）**
   - 用仓库自带工具 `support/cursor-protocol-extractor` 从本机安装的 Cursor **3.27.22** 重新提取 proto：
     ```bash
     cd /Users/pittcat/Dev/Rust/cursor-byok/support/cursor-protocol-extractor
     GOPROXY=https://goproxy.cn,direct GOSUMDB=off \
     go run ./extractor \
       -input "/Applications/Cursor.app/Contents/Resources/app/extensions/cursor-agent-host/dist/main.js" \
       -input "/Applications/Cursor.app/Contents/Resources/app/out/vs/workbench/workbench.glass.main.js" \
       -output /tmp/proto-new -skip-format -strict
     ```
     （`proxy.golang.org` 会超时，必须用 `goproxy.cn`；校验阶段会在 `agent_v1.proto:12112` 报错，但产物已生成在 `/tmp/proto-new/`。）
   - 与 `protocols/cursor/agent_v1.proto` 对比结果：
     - `ConversationStateStructure`：字段 **1–31 完全一致**（含 27 = `conversation_started_time_zone`），客户端新增 32–47（`goal_state`、`is_root_project_conversation`、`turn_telemetry`、`voice_call_*` 等）。
     - `AgentRunRequest`：仓库多出 10 `suggest_next_prompt`、27 `client_supports_prompt_context_usage_rpc`（客户端无）；客户端新增 28–36。
     - `AgentClientMessage`：8 个 oneof 字段完全一致。
     - 结论：**纯新增字段的协议漂移**。按 protobuf 语义 unknown fields 应被跳过，合法消息不可能因此解码失败。

5. **确认安装包内的 proto 与仓库一致（已确认）**
   - `strings -a "/Applications/Cursor BYOK.app/Contents/MacOS/cursor-byok-desktop"` 能查到 `subagent_state_refs`、`communicate_update_final_summary`（字段 31 及以前），查不到新客户端才有的 `transcript_parent_conversation_id`。
   - 即：应用 1.0.1 的生成代码 == `protocols/cursor/agent_v1.proto`，不存在「安装包比仓库更旧」的额外变量。

6. **客户端发送路径（已确认）**
   - 发送方是 Cursor 的 **agent-host 扩展**：`/Applications/Cursor.app/Contents/Resources/app/extensions/cursor-agent-host/dist/main.js`，类 `xs`（BidiTransport）。
   - 关键代码：`const k = _.value.toBinary(); I = this.binaryEncoding ? {dataBinary:k} : {data:Buffer.from(k).toString("hex")}`
   - `binaryEncoding` 为 false（否则服务端会报 `BidiAppend data_binary is not part of the captured protocol`，与现象不符）。
   - 请求构造：`new v.Mpn({conversationState:t, action:..., ...})` → `new _.KS({message:{case:"runRequest", value:pe}})`。
   - 3.27.22 新增：先尝试 WebSocket `GET /agent/v1/run`（`AgentRunWebSocket`），冷池失败后才回落 HTTP `BidiAppend`；回落前会等待约 **60 秒**。

7. **抓包尝试（部分成功）**
   - 编写 `/tmp/capture_proxy.py`：在 `127.0.0.1:58598` 监听 CONNECT，用 `~/.cursor-byok-v3/ca/ca.crt|ca.key` 签发叶子证书做 TLS 终止，再 TLS 连回 58597，双向原样转发，并把 client→upstream 原始字节落盘到 `/tmp/byok-capture/raw-*.bin`。

   - 结论（已确认）：**BidiAppend 这条链路不经过 `http.proxy` 设置**，它由另外的机制直达 58597/58317（具体机制未确认）。

# 关键决策和理由

1. **先比对 schema 再谈修复**：避免贸然重生成 proto 掩盖真实原因。事实证明这一步直接排除了最常见的猜测。
2. **用真实安装包提取 schema，而不是相信仓库**：仓库 proto 提取自 2026-08-29，Cursor 是 10-27 更新；必须确认二者差异。
3. **坚持抓真实字节**：目前所有静态证据都表明「合法消息应当能解码」，因此剩余可能性（新编码/新包装/不同 schema 的 state 对象）只能靠字节判定。
4. **抓包选择本地 MITM 而不是重编译服务端**：重编译 Tauri 应用成本高，且需要改动用户运行环境；MITM 方案可完全还原（已还原）。
5. **结束时恢复环境**：已把 Cursor `http.proxy` 改回 58597 并停掉 `/tmp/capture_proxy.py`；备份在 `/tmp/cursor-settings.backup.json`。

### 优先级 2：拿到失败请求的 `data` 十六进制

- 方案 A（推荐，最直接）：在 `server/src/api/cursor/bidi.rs` 的 decode 失败处，把 `payload` 前若干 KB 以 hex 打到日志或写入 `/tmp`。需要能构建并运行该服务端（1.0.1 的 Tauri 应用内嵌服务端；可行路径是构建 desktop 应用或以 standalone `cursor-server` 运行并接管代理，未验证）。

- 方案 C：改造 `support/cursor-capture`（现成的 HTTP 反向代理 + BidiAppend hex 解码器），把 Cursor 指到它，但它需要能设置后端 URL 的入口。

### 优先级 3：分析字节

拿到 hex 后：
```bash
xxd -r -p payload.hex > payload.bin
protoc --decode_raw < payload.bin | head -50
protoc --decode=agent.v1.AgentClientMessage -I /tmp/proto-new /tmp/proto-new/agent_v1.proto < payload.bin
```
重点看 `conversation_state`（field 1）的首字节与 tag，与 `ConversationStateStructure` 的合法字段号（1,3,4,5,6,7,8,9,...,31,32...）比对。

### 优先级 4：按根因落修复

- 若确认是客户端对 `conversation_state` 使用了新编码/新包装：在 `bidi::decode` 层做兼容解码，或改用「解码失败时把该字段当作不透明 bytes 透传」的策略。
- 若只是顺序问题：把 `handlers.rs` 的模型判定提前到解码之前，至少恢复原生模型转发能力。
- 修复后补测试：`server/tests/interrupt.rs`、`server/tests/conversation_delivery.rs` 已有构造 `AgentClientMessage` 的辅助函数，可作为回归测试落点。
